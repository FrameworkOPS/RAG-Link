# Build Philosophy

## Core principle

**Build the operating system of Framework OPS itself before building client-facing tools.**

A fractional COO selling operational discipline must run a disciplined operation. The internal systems become a sales asset only if prospects see them — so build in public on LinkedIn.

## The test for every build

Every tool/system/process built must map to either:
- **(a) Closing first 3 clients**, OR
- **(b) Delivering to them efficiently**

If neither, cut it. No exceptions during 60-day pre-launch.

## Compounding work principle

Prioritize builds where the work compounds:
- ClickUp API script (Week 1) → 60% of engagement template generator (Week 3-4)
- Audit deliverable template (Week 4) → 80% of audit generator (Week 5)
- Daniel engagement (ongoing) → case study (Week 6) → outreach proof (Week 8)

Avoid one-off tools that don't extend anything else.

## Build vs. buy vs. defer

**Build** when:
- The tool is core to differentiation (engagement template generator, audit system)
- No off-the-shelf solution fits the workflow
- The build creates reusable IP

**Buy** when:
- Solved problem with mature tools (Cal.com, Tally, Instantly)
- Total cost of ownership (build + maintain) exceeds 12-month SaaS cost
- The category isn't a differentiator

**Defer** when:
- Need is hypothetical (no client has asked)
- Would be 10% used (over-engineering for solo)
- Phase 2+ category per [[deferred-to-phase-2]]

## 80% rule

Ship 80% versions. Perfectionism slides the launch date, and the launch date is fixed.

What "good enough" means:
- Functional, tested with one real use case
- Documented enough to use again
- Known limitations written down
- Polish remains as Phase 2 task

## Build-in-public requirement

Every internal build doubles as marketing content:
- Screenshots
- "Here's why I built this"
- Tactical breakdown of mechanism
- Real numbers (time saved, problems solved)

Posts the build → builds the post.

This doubles ROI of internal builds because they're also content assets.

## What NOT to build

See [[deferred-to-phase-2]] for explicit no-build list.

Tempting categories to resist:
- "Cool" tech demos (anything with AI in the name that isn't core)
- Generic productivity tools (already commoditized)
- Branding/visual polish beyond minimum viable
- Internal dashboards "for tracking" without specific decisions they drive

## Solo operator considerations

The biggest mistake disorganized founders make pre-revenue: **building infrastructure for a business that doesn't exist yet.**

Mitigation:
- Hard deadline on calendar (July 5, 2026)
- Weekly checkpoint accountability
- Revenue, not readiness, is the success metric
- Always ask: "Would a client paying $5K notice this?" If no, deprioritize.
